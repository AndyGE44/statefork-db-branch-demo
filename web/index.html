DB Branch Is Not Enough

Dolt and Neon-style database branches roll back the database correctly. This demo shows the scope problem: an agent retry also depends on generated files, warm cache/process state, a search index, and the shell session. A partial rollback can leave those layers drifted; StateFork + Waypoint restores the whole session boundary.

Scenario: a checkout migration crosses four state layers

We start with a tiny e-commerce checkout service. The product price is stored in the database as dollars, the backend reads a filesystem file named schema_version.json to know that unit, and Redis already has a warm cart-total cache. A separate SQLite FTS search index powers the storefront listing, outside the Dolt checkout.

The agent has reached a useful intermediate state: the service is running, the cart is warmed, and the bug or migration target is understood. It wants to compare two candidate fixes. First it tries Fix A, a dollars-to-cents migration. If Fix A is not the path it wants, the agent must roll back to the warm baseline before trying Fix B.

The rollback is the point of the demo. Fix B is only trustworthy if it starts from the same clean branch point, not from a half-restored environment where the database says one thing and the config, cache, or search index say another.

What StateFork adds at the end

This demo follows the rewind-button pattern: snapshot a valuable mid-task state, try Fix A, restore, then try Fix B from the same baseline. StateFork is useful because it treats the branch point as the working session, not just the database table.

  • Trustworthy retriesFix B starts from DB, config, cache, search index, shell, and process state that agree with each other.
  • Less wasted setupThe agent does not need to rebuild the service, rewarm caches, and rediscover the same context for every attempt.
  • Real explorationThe agent can compare candidate paths from a shared checkpoint and keep the branch that works.
